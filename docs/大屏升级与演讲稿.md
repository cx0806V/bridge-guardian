## 一、大屏升级设计说明

### 1.1 设计目标与信息架构

升级后的大屏采用「全局态势 → 关键指标 → 风险预警 → 处置闭环 → 设备/桥梁详情」五层信息架构，视觉节奏参考工业监控类科技大屏（深色底 + 冷色发光 + 面板切角），但所有信息均来自真实接口数据，动效克制、每一处都有含义。

**首屏记忆点设计逻辑**：评委抬头第一眼，要在 3 秒内回答三个问题——
1. **守护什么**：顶部电影化标题栏「桥体卫士 · 桥梁结构健康监测」+ Hero 区桥梁结构 SVG，直接点明对象是"桥"；
2. **风险状态如何**：Hero 区中央的风险总状态（安全/预警/报警/严重报警/设备离线）用整屏最大字号与最高亮度呈现，颜色即结论；
3. **系统价值在哪**：下方依次铺开关键指标、趋势预警与报警处置队列，一眼可见"发现—预警—处置"的闭环正在运转。

### 1.2 五层信息架构详述

| 层 | 布局位置 | 承载信息 | 视觉处理 | 动效设计（克制、有意义） |
|---|---|---|---|---|
| **① 全局态势（Hero）** | 首屏上半部中央，占据视觉焦点 | 桥梁结构 SVG 线稿、测点分布、全局风险总状态、当前应变指标大数字 | 深蓝渐变底（`#07121f` 系），桥梁 SVG 用青色（`#3fd0ff`）描边发光；风险状态用全屏最大字号，颜色随等级切换（绿/黄/橙/红/灰） | 测点风险波纹：正常时测点为静止微光点，进入预警后对应测点泛起扩散波纹（颜色随等级）；风险卡轻微"呼吸"明暗，提示"系统活着"；等级跃迁瞬间有一次短促的高亮脉冲 |
| **② 关键指标** | Hero 下方横排四张发光指标卡 | 当前风险（应变值/阈值/变化率）、设备健康度（心跳/连接状态/最近异常）、待处置报警数（含预警/报警/严重分级计数）、系统运行（时长/周期/累计采样） | 面板切角 + 细描边 + 内发光；关键数字用大号等宽字体；待处置数 >0 时由青转红 | 数字刷新时轻微过渡；待处置报警数变为非零时卡片边缘泛红光一次，之后保持静态——**不持续闪烁干扰** |
| **③ 风险预警** | 中部图表区（趋势图 + 阈值仪表左右排布） | 受载趋势曲线（含阈值虚线 markLine）、阈值仪表（绿/黄/橙/红四段色弧） | 曲线青色发光 + 渐变面积填充；阈值线为红色虚线；仪表四段色带与风险等级同色系，保证"颜色语言全局一致" | 曲线随采样逐点推进；越阈瞬间阈值虚线处有一次扫光提示；**新告警高亮**：对应时刻的告警横条/表格行以 1 秒渐显高亮，随后回归常态 |
| **④ 处置闭环** | 下部通栏：报警处置队列 + 最新告警横条 | 报警表格（时间/应变指标/等级/规则/原因/状态/操作）、点击行展开详情（触发规则/触发值/触发时间/处置状态）、「确认处理」按钮；顶部最新告警横条轮播当前未处理事件 | 等级徽章四色（预警黄/报警橙/严重红/信息青）；未处理行权重更高，已处理行降透明度 | 新告警行入场时一次渐显高亮；点击「确认处理」后状态平滑切换为"已完成"；离线时表格不清空、不沿用旧值 |
| **⑤ 设备/桥梁详情** | 贯穿侧栏与顶部状态条 | 设备健康度三要素（心跳时间戳/连续超时/最近错误）、系统运行状态、数据源徽章（串口真实/模拟）、模拟场景面板、模拟水印 | 数据源徽章：串口模式高亮"真实"，模拟模式常显水印横条「模拟演示 · 非真实硬件数据」；场景按钮与风险等级同色 | 离线时 Hero 区测点波纹熄灭、仪表读数显示 `--`（不伪造）、健康度状态点由绿变灰；恢复时一次由灰到绿的过渡 |

**动效总原则**：发光只给"当前最重要的一件事"——风险状态；波纹只在有风险时出现；高亮只做一次入场提示。静止 = 安全，这本身就是信息。

### 1.3 与现有实施的对应

升级在现有 `templates/dashboard.html` 结构上增强，不重写数据链路：顶部标题栏 + 实时时钟、Hero 全局态势区（桥梁 SVG + 测点风险波纹）、关键指标发光卡、趋势图 + 阈值仪表、设备健康度与系统运行面板、报警处置队列 + 最新告警横条，均沿用 `/api/data` 接口现有字段（strain/threshold/rate/alarms/device_health/uptime 等），风险分级沿用四级口径（≤阈值安全、≤1.1 倍预警、≤1.2 倍报警、>1.2 倍严重报警，与 `rules.py::_level` 和前端 `riskOf()` 一致）。

### 1.4 中央「桥梁结构三维可视化场景」（可操控）

> 口径提醒：演讲时称它**「桥梁结构三维可视化场景」**即可（文档标题沿用了界面上的「数字孪生场景」字样，视觉风格参考，不自称具备数字孪生所需的实时数据同化能力）。模型是**按公开设计参数做的几何示意**，不是实测模型。

**对象**：花江峡谷大桥（六安高速，贵州省）——世界最高桥，公开设计参数：主跨 1420m 双塔单跨钢桁梁悬索桥、缆跨 245+1420+495m、主缆垂跨比 1/10、主缆中心距 27m、桥面宽 25.5m（双向 4 车道）、桥面至水面 625m、板桁结合钢桁梁（桁高 8m / 桁宽 27m / 标准节段 15.4m）、吊索 φ64mm（每吊点 2 根、骑跨式索夹）、锻焊结合式索鞍、六枝岸隧道锚 + 安龙岸重力锚、抗风措施为「中央稳定板 + 上/下水平导流板」、桥旅融合（塔顶观星水吧 230m²、观光电梯、桁内玻璃观光厅）。

**实现方式**：three.js（WebGL）程序化建模 + OrbitControls 轨道控制，**全部依赖已本地化到 `static/vendor/`，断网可用**（现场无外网也能演示；CDN 只在本地加载失败时兜底）。

| 文件 | 职责 |
|---|---|
| `static/js/three-boot.js` | 注入 importmap 并从本地加载 three r160 + OrbitControls |
| `static/js/twin/spec.js` | **公开设计参数表**（可逐项核对）+ 精度声明 `FIDELITY_NOTE` |
| `static/js/twin/geom.js` | 梁段矩阵/几何工厂、矩阵合并、抛物线主缆、确定性噪声 |
| `static/js/twin/materials.js` | 材质与主题色（风险等级换色，颜色插值避免突变） |
| `static/js/twin/canyon.js` | 峡谷地形（解析地形函数 + 分形噪声）、北盘江水面、峡谷雾气 |
| `static/js/twin/bridge.js` | 整桥模型：钢桁梁（140 节段）、主缆/背索（垂跨比 1/10）、吊索（256 根）、双塔（含塔顶水吧/观光电梯）、锚碇、7 个监测热点 |
| `static/js/twin/scene.js` | 渲染器/相机/光照/环境贴图、轨道控制、预设视角、拾取、风险联动 |
| `static/js/twin/hud.js` | 场景内 HUD：参数卡、视角与开关、热点详情 |
| `static/js/twin/mount.js` | 挂载入口 + **诚实降级**（WebGL 不可用 → 二维示意图并显示原因） |

**可操控能力（答辩可现场演示）**：

| 操作 | 效果 |
|---|---|
| 左键拖拽 / 触屏单指 | 绕桥旋转 |
| 滚轮 / 双指捏合 | 缩放（25m ~ 6200m） |
| 右键拖拽 / 双指拖动 | 平移 |
| 双击模型任意位置 | 以该点为中心平滑飞行聚焦 |
| 单击测点标记 | 弹出该部位说明（测点编号 + 说明 + 模型坐标） |
| HUD 视角预设 | 全桥 / 主跨 / 桥塔 / 峡谷 / 桥面，另有放大缩小与复位 |

**与监测数据的联动（同一份 `/api/data`，不另造数据）**：风险等级 → 全场主题色（安全青 `#3fd0ff` / 预警琥珀 / 报警橙 / 严重报警红 / 离线灰）+ 测点涟漪节奏（等级越高越急促，离线冻结）；相对荷载（当前值/阈值）→ 吊索发光强度（仅视觉表达，**不是实测内力**）；跨中测点读数由 3D 场景投影到 HTML 标签，数值与左侧风险卡同源。

**精度与诚实边界（评委问答要点）**：

- 主跨、缆跨、垂跨比、桁高桁宽、节段长度、桥面宽度、桥高、锚碇高度：**公开设计参数**，代码注释与 `spec.js` 中逐项标注来源；
- 塔柱收坡率、横梁道数、承台桩基、锚碇体量、峡谷具体地形：**按公开效果图与同类桥比例的示意补全**，界面上以「几何口径」脚注明确写出，不作为工程测量依据；
- 场景里的吊索发光强弱是「相对荷载」的视觉映射，**不声称是内力计算或有限元结果**；
- WebGL 不可用时如实降级为二维示意图并写明原因（`#sceneFallback`），不静默假装 3D 可用。

## 三、创新点提炼（模式创新）

### 1. 从分散监测到「一屏统管」的管理模式创新
**一句话**：把采集、研判、预警、处置、追溯五个环节收拢到一块屏上，管理者不再需要辗转多个工具。
**展开**：传统做法里，数据在采集器里、判断在人脑里、记录在纸质台账里。桥体卫士把"风险总状态—关键指标—趋势预警—处置队列—设备健康"按五层信息架构整合为一屏，风险颜色即结论、处置按钮即动作，管理动作与数据状态同屏闭环。
**证据锚点**：`templates/dashboard.html` 五层布局与 `/api/data` 单接口聚合；报警行内「确认处理」按钮（`acknowledgeAlarm`）；演示：大屏一页完成"看到→判断→处置"。

### 2. 从人工巡检、被动发现到数据驱动、主动预警的治理创新
**一句话**：不等巡检发现问题，让数据在越阈的瞬间自己"开口说话"。
**展开**：系统以默认 1 秒周期逐点研判，6 类规则覆盖"超限、突变、持续、波动、漂移、离线"六种风险形态；边沿触发加滞回设计保证持续超限不刷屏——预警是"一次有效提醒"，不是"噪音轰炸"。即使上位机没开，硬件端蜂鸣器与红灯照样本地预警，主动预警不依赖单一节点。
**证据锚点**：`rules.py`（边沿触发 + 滞回）；`tests/test_rules.py::test_threshold_no_duplicate`；`firmware/main.py` 本地声光预警；现场声光演示。

### 3. 多维数据融合，让风险可感知、可定位、可追溯
**一句话**：风险不只是一个红点，而是"在哪个测点、因哪条规则、触发值多少"的完整事实。
**展开**：大屏将应变值、变化率、阈值、设备心跳、报警原因多维信息融合呈现；Hero 区测点波纹把风险定位到桥梁结构的具体位置；每条报警带 `rule + reason`（如"应变指标 135.00 超过阈值 120.00"），从历史页可回溯任意事件的来龙去脉。
**证据锚点**：`rules.py` reason 文案；`dashboard.html` 报警详情面板（触发规则/触发值/触发时间/处置状态）；`db.py` 五表统一时间/设备/状态字段。

### 4. 预警与处置闭环联动，让安全管理更及时、更可执行
**一句话**：报警不是终点——"确认处理"让每一条告警都有人认领、有状态、有交代。
**展开**：待处置计数卡在报警出现的瞬间变红，处置动作一键完成并留痕；设备离线触发严重报警、恢复自动记录"设备恢复"，连设备自身的异常也纳入同一个闭环。参数变更进审计表，谁在何时改了阈值全程可查——闭环覆盖"事"也覆盖"人"。
**证据锚点**：`app.py::acknowledge_alarm` + `_record_device_event`；`db.py` audit 表 + 设置页「最近变更记录」；`tests/test_device.py`。

### 5. 用直观可视化降低管理决策门槛，让复杂桥梁安全状态「一眼可知」
**一句话**：不懂应变力学的管理者，也能凭颜色和形状 3 秒看懂"现在安不安全"。
**展开**：四级风险用全局一致的绿/黄/橙/红颜色语言表达；阈值仪表把"离危险还有多远"变成仪表指针的位置；趋势图上的阈值虚线让"越没越线"无需解释。同时界面坚持诚实：模拟模式常显水印、断线如实显示离线、离线时仪表显示 `--` 而不沿用旧值——可视化降低的是理解门槛，不是诚信门槛。
**证据锚点**：`dashboard.html`（riskOf 四级分级、demoBanner 模拟水印、离线 `--` 处理）；`datasource.py` 设备健康度三要素（心跳+超时+最近错误）；离线降级演示。

## 四、答辩演讲稿

### （A）完整版（5–8 分钟现场路演版，约 1470 字）

各位评委好。

试想象这样一个深夜：一座桥梁在风雨中默默承载，某处构件的受力曲线正悄悄偏离正常区间——没有告警，没有人看见，直到第二天巡检人员到场。桥梁安全管理的痛点，往往不在"没有数据"，而在风险发生的那一刻：无人知晓、无人响应、事后无据可查。

我们的作品「桥体卫士」，就是回应这个痛点的。先说明一个诚实的边界：它是一套"缩尺桥梁模型受载变化模拟"的完整监测原型。我们用一块 ESP32、一个压力传感器和一套 Flask Web 平台，把"采集—判断—存储—展示—处置"这条链路完整跑通，用缩尺模型演示桥梁安全监测的管理逻辑。它模拟的是受载变化，不声称替代工程级监测设备——这个边界，我们全程坚守。

请大家看身后这块大屏。这是升级后的监测界面：中央是桥梁结构的全局态势，每一个测点的状态实时可见；这条平稳的蓝色曲线，就是缩尺模型此刻的受载数据。系统每秒采集一次，规则引擎逐点研判。

现在，凌晨两点的场景在这里重演：应变曲线悄然越过预警线，系统在下一个采样周期内就完成判断——大屏风险状态由绿转橙，对应测点泛起风险波纹，报警队列弹出一条记录。请注意这条记录的内容：它不只说"超了"，而是写清"哪条规则触发、触发值多少、阈值多少"。这样的规则我们有六类：阈值超限、变化率突变、持续超限、短时波动、基线偏移，外加设备离线。每条报警都可解释，评委看到的是一个事实，而不是一个红点。

与此同时，硬件端的蜂鸣器响起、红灯亮起——即使电脑没开，本地预警依然生效。这是双重保障。

接下来是处置。值班人员点击"确认处理"，这条报警的状态从"未处理"变为"已完成"，处置留痕。待处置计数归零，卡片由红回青。从发现到响应到处置，闭环在这块屏上完成。事后，历史页有风险事件时间线、统计摘要和 CSV 导出；谁在何时调整过阈值，审计记录一查便知。

在功能之上，请允许我提炼这个作品真正想表达的五点模式创新：

第一，从分散监测到一屏统管——采集、研判、预警、处置、追溯，五个环节收拢于一块屏，管理动作与数据状态同屏闭环。

第二，从人工巡检、被动发现到数据驱动、主动预警——数据在越阈的瞬间自己开口说话，而且边沿触发加滞回的设计，保证预警是一次有效提醒，而不是噪音轰炸。

第三，多维数据融合——风险可感知、可定位、可追溯：在哪个测点、因哪条规则、触发值多少，每条报警都是一个完整的事实。

第四，预警与处置闭环联动——报警不是终点，每一条告警都有人认领、有状态、有交代；连设备离线这样的自身异常，也纳入同一个闭环。

第五，用直观可视化降低决策门槛——全局一致的颜色语言，让不懂力学的管理者也能一眼看懂"现在安不安全"。而这一切可视化的前提，是诚实：模拟模式常显水印，断线如实显示离线，离线的仪表绝不沿用旧值。

这套系统的价值，可以概括为三个"更"：**更早发现风险**——预警级提示在超限初期即出现，基线偏移规则能捕捉缓慢漂移；**更快响应事件**——本地声光与 Web 同步双通道，处置一键闭环；**更科学决策**——可解释的报警原因、可追溯的审计记录、可导出的历史数据，让每一次决策有据可依。

工程化方面，密钥走环境变量、所有接口统一鉴权、写接口带 CSRF 防护，101 项自动化测试用例全部通过。我们也诚实地承认限制：这是单设备缩尺原型，输出的是相对应变指标，采样周期为秒级——要走向真实桥梁，还需要工程级传感器、标定与长期验证。这一步的差距，我们不回避。

但我们相信，安全管理的本质，是在风险酿成事故之前，有人看见、有人响应、有据可查。

### （B）精简版（2–3 分钟，约 480 字）

各位评委好，我们的作品是「桥体卫士」——一套"缩尺桥梁模型受载变化模拟"的完整监测原型。硬件是 ESP32 加压力传感器，软件是 Flask Web 平台加一块全新升级的可视化大屏。先说明边界：它演示的是受载变化监测的完整链路，不声称替代工程级设备。

它做四件事。第一，**感知**：每秒采集，大屏全局态势区实时呈现测点状态与受载曲线。第二，**研判**：6 类可解释规则，当曲线越过预警线，系统立即分级变色、弹出报警，并写清"哪条规则、触发值多少"——每条报警都答得出"为什么"。第三，**处置**：一键确认处理，状态闭环留痕；硬件端蜂鸣器红灯同步本地预警，不依赖上位机。第四，**追溯**：历史页时间线、统计与导出，参数变更全程审计。

创新上是五个转变：分散监测到一屏统管、被动发现到主动预警、模糊告警到可解释可定位、报警终点到处置闭环、专业门槛到一眼可知。价值是三个"更"：更早发现风险、更快响应事件、更科学决策。

工程化上，101 项自动化测试用例全绿；诚信底线上，模拟常显水印、断线如实离线、绝不伪造数据。
