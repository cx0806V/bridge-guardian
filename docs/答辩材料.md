## 二、讲稿

### （A）完整版（5–8 分钟，约 1400 字）

**开场（30 秒）**
各位评委好，我们是软件技术专业的团队，作品是「桥体卫士」——一个桥梁结构健康监测的缩尺原型。我们用一块 ESP32、一个压力传感器、一块 OLED 和一套 Flask Web 平台，实现了从传感器采集、本地预警、到 Web 实时监测、报警处置和历史追溯的完整闭环。

**背景（40 秒）**
桥梁长期受载，结构健康关乎安全。但真实的工程级应变监测，设备贵、部署难。我们做的是一个缩尺模型原型——用来完整演示「采集 → 判断 → 存储 → 展示 → 处置」这条链路。这里我要先说明一个诚实的边界：它模拟的是桥梁受载变化，不是经工程标定的真实桥梁监测，我们不会夸大它的精度。

**架构（50 秒）**
整个系统分六层：硬件层、采集层、规则引擎、数据层、服务层、展示层。核心设计是采集层的「数据源抽象」——模拟器和真实串口实现同一个接口，用环境变量一键切换。这意味着：同样的报警判断、同样的存储、同样的界面，换数据源不用改任何上层代码。

**双模式与健康度（50 秒）**
现场我们用的是串口 USB 直连，不依赖网络，最稳。设备健康度由三要素构成：心跳时间戳、连续超时计数、最近错误。拔掉 USB，大屏立刻如实显示「设备离线」，我们绝不伪造在线状态或数据。

**可解释报警（60 秒）**
报警引擎有 6 类规则：阈值超限、变化率突变、持续超限、短时波动、基线偏移，还有设备离线。每条报警都带「触发规则」和「原因」——比如「应变值 135 微应变，超过阈值 120」。评委看到的不只是一个红点，而是「为什么报警」。规则用边沿触发加滞回，避免持续超限时刷屏。

**数据与审计（40 秒）**
数据统一存 SQLite，五张表：采样、心跳、报警、设置、审计。谁在何时改了阈值，都留痕。历史数据支持时间筛选、统计、CSV 导出。

**安全与工程化（40 秒）**
密钥走环境变量，不硬编码；所有页面和 API 统一鉴权，未登录访问返回 401；写接口受保护。我们有 37 项自动化测试，全部通过。

**硬件闭环（40 秒）**
硬件端：HX711 采集压力，OLED 实时显示，超过阈值本地蜂鸣器和红灯就报警——即使电脑没开，硬件也能本地预警，这是双重保障。

**总结（30 秒）**
总结一下：我们做的是低成本、可验证、可解释、可追溯、可兜底的完整监测闭环。请评委看演示，眼见为实。

## 六、高压评委问答（30 题）

**Q1 为什么用称重/压力传感器来模拟应变？**
A：应变片需要工程级标定和专门测量电路，成本高。我们用 HX711 压力传感器测量模型的受载，把载荷变化映射为相对应变（με），目的是演示「受载 → 报警 → 处置」的完整链路，而不是宣称测出真实微应变。

**Q2 精度如何保证？数值可信吗？**
A：我们诚实声明，输出是「相对应变」，未经工程标定，不做精度承诺。我们保证的是「数值随载荷单调、稳定变化」，并用标定流程让读数可复现；规则的合理性靠边沿触发与滞回保证，不靠虚假精度。

**Q3 为什么不直接上云？**
A：现场演示最怕网络不稳。我们用串口 USB 直连，点对点、离线可跑、可验证。MQTT 需要 broker、HTTP 依赖路由器，都增加现场不确定性。上云不是不能用，而是不是当前最优解。

**Q4 数据是真实的吗？有没有造假？**
A：真实。模拟模式是明确标注的「模拟数据」；真实模式下数据来自 ESP32 串口上行，断线立即显示离线，我们**不伪造在线、不伪造数据**。这本身是设计红线。

**Q5 断网了怎么办？**
A：系统不依赖网络。串口直连 + ECharts 本地化，断网照样采集、报警、展示。设备离线则是另一回事——会如实显示离线并触发「设备离线」报警。

**Q6 你们和普通监控系统有什么差异？**
A：三点：一是可解释报警（每条说清为什么）；二是设备健康度与离线诚实呈现；三是完整工程化（审计、测试、兜底）。多数演示项目只做到「画个曲线」，我们做到了「采集→判断→存储→处置」的闭环。

**Q7 要扩展到真实桥梁，还缺什么？**
A：缺的是工程级应变片、桥路标定、长期稳定性验证、边缘与云端冗余、以及符合规范的传感器安装。我们做的是原型，诚实承认这一步的差距。

**Q8 报警阈值怎么定的？合理吗？**
A：阈值可在设置页调（1–200 με），规则内部参数（变化率、持续点数、波动/漂移阈值）集中在 `rules.py`。默认值用于演示，工程上应结合结构力学与历史数据标定，我们没有数据支撑，故不声称最优。

**Q9 为什么用串口不用 HTTP/MQTT？（追问细节）**
A：串口复杂度最低、可离线、断线状态明确、字节流可现场抓包验证。HTTP 需要路由器，MQTT 需要 broker，都是现场的不确定因素。

**Q10 持续超限会不会刷屏？**
A：不会。规则用边沿触发——阈值超限只在「进入超限的瞬间」报一次；持续超限只在连续 N 点后报一次；回到安全区才重置。有测试覆盖。

**Q11 短时波动和基线偏移分别防什么？**
A：短时波动捕捉「毛刺」——窗口内峰谷差过大；基线偏移捕捉「缓慢漂移」——近期均值相对历史基线偏移。两者和阈值、变化率互补。

**Q12 设备离线是怎么判定和恢复的？**
A：心跳 + 连续超时计数，超过阈值判离线并触发「设备离线」严重报警；恢复在线时自动记录「设备恢复」，状态闭环。

**Q13 数据存哪里？会不会丢？**
A：SQLite，五张表：采样、心跳、报警、设置、审计。统一时间/设备/状态字段，支持 CSV 导出。

**Q14 有人改了参数能查到吗？**
A：能。每次改阈值/周期都写审计表，设置页有「最近变更记录」，谁在何时改了什么一目了然。

**Q15 安全性呢？**
A：账号密钥走环境变量不硬编码；所有页面/API 统一鉴权，未登录 API 返回 401；写接口受保护；前端做 XSS 转义。

**Q16 你们有没有用 AI/机器学习？**
A：没有，也不需要。在缺乏真实标注数据时，用可解释规则更可靠、更可答辩。我们明确不做「未经验证的预测算法冒充智能预警」。

**Q17 变化率和运行时长是大屏指标，怎么算的？**
A：变化率是相邻采样点差值；运行时长是进程启动至今。都由后端实时计算下发。

**Q18 采样周期多少？实时性如何？**
A：默认 1 秒，可调 0.1–60 秒。这不是毫秒级实时系统，但满足监测演示需求。

**Q19 如果同时多台设备接入？**
A：当前是单设备原型。数据模型已含 `device_id` 字段，扩展多设备只需串口/数据源层支持多路，上层不变——这是我们预留的扩展点，但尚未实现。

**Q20 SQLite 够用吗？为什么不换 MySQL？**
A：单机、数据量小，SQLite 零部署、事务可靠、可单文件迁移，最适合现场演示。换成 MySQL 对当前场景是过度设计。

**Q21 测试覆盖了什么？**
A：规则引擎（含防刷屏、等级分级）、数据层 CRUD、鉴权、API 端到端、设备心跳/离线、串口数据链路，共 37 项全绿。

**Q22 硬件标定怎么做？**
A：HX711 输出原始 24 位读数，标定零点（空载）和比例系数（已知载荷）。标定只保证读数随载荷单调稳定，不声称工程精度。

**Q23 OLED/LED/蜂鸣器的作用？**
A：本地预警。即使上位机没启动，硬件也能声光报警，双重保障。

**Q24 为什么用 MicroPython 写固件？**
A：团队熟悉 Python，迭代快；HX711 读取我们直接实现，不依赖第三方库，代码可控、可答辩。

**Q25 单点故障怎么办？**
A：诚实的回答是——当前是单设备原型，没有做冗余。但「模拟/真实」双模式本身提供了演示兜底：硬件突发故障可切模拟模式继续演示。

**Q26 数据量大了性能怎么办？**
A：历史查询用 `LIMIT` 分页、按时间索引，避免全表加载；实时曲线只保留最近 60 点。当前规模无性能问题。

**Q27 部署复杂吗？**
A：不复杂。`pip install -r requirements.txt` 后 `python app.py` 即可，`.env` 配好数据源与串口参数，有现场启动手册。

**Q28 为什么历史页要动态同步阈值？**
A：否则设置页改了阈值后，历史页的「超限次数」和阈值线还是旧值，口径不一致。我们让历史页实时拉取当前生效阈值，保证三端一致。

**Q29 你们团队怎么分工的？**
A：组长负责架构与数据层，后端负责规则引擎与安全，前端负责大屏与可视化，硬件负责固件与标定。每人的贡献都能在代码/演示中指出。

**Q30 这个项目最大的价值是什么？**
A：不是炫技，而是「诚实地把一个监测系统做完整」——采集、判断、存储、展示、处置、审计、测试全闭环，且每个报警都可解释、每次断线都不造假。

**Q31 如果评委说「这不就是个大屏展示吗」？**
A：大屏只是最后一层。真正的价值在采集层的双模式抽象、规则引擎的可解释性、设备健康度的诚实呈现，以及 SQLite 审计与 37 项测试支撑的工程化——这些是「展示」背后的真东西。

**Q32 数据有没有做异常值处理？**
A：串口层会丢弃无法解析的行（非 JSON/非数字）；规则层的「短时波动」可捕捉毛刺；但采样值本身未做更复杂的滤波，如实呈现。

## 八、第二轮新增评委追问（P0/P1 收口后）

**Q33 为什么称重/压力传感器能用于本原型？（追问本质）**
A：它测的是「载荷 → 受力 → 原始 ADC 读数」的映射，不是真实微应变。我们用 HX711 把模型受载变化转成单调、稳定的读数，用来演示「受载 → 报警 → 处置」闭环。它适合本原型，是因为原型要证明的是**链路完整性**，不是**测量精度**。

**Q34 你们的单位到底是什么？为什么不用微应变？**
A：我们明确区分两个量：`raw_value` 是 HX711 原始 ADC 读数（无量纲计数），`calibrated_value` 是相对应变指标（无量纲）。之所以不写微应变，是因为微应变需要应变片 + 工程级标定，我们没有做、也不声称。界面和文档统一标注「相对应变指标」，不混用单位。

**Q35 精度到底怎么得出的？**
A：我们还没得出——本轮产出的是可复现的标定流程和测试记录模板，真实数据要等硬件在场实测填入。在数据出来之前，任何精度结论都写「待实测」。这是刻意的诚实设计。

**Q36 断线了，历史数据会丢吗？旧值会继续显示吗？**
A：不会。数据每条实时落盘 SQLite，断线不影响已存历史；断线后串口层返回「离线」，大屏如实显示离线并触发「设备离线」报警，**不沿用旧值制造在线假象**。

**Q37 为什么不用云端 / AI？**
A：串口 USB 直连点对点、离线可跑、可现场抓包验证，最适合比赛现场；上云/MQTT 引入 broker 和网络依赖，增加不确定性。AI 需要真实标注数据，在无数据时用可解释规则更可靠、更可答辩。我们不做「未经验证的预测算法冒充智能预警」。

**Q38 你们的 CSRF 和密码是怎么处理的？**
A：所有 POST/PUT/PATCH/DELETE 接口都做 CSRF 防护（基于 Session 的同步令牌校验，Synchronizer Token Pattern），前端 fetch 统一带 `X-CSRF-Token` 头；Session Cookie 设 HttpOnly + SameSite=Lax；密码支持 SHA-256 摘要存储（`APP_PASSWORD_HASH`，后续可升级 PBKDF2），不把真实密钥/密码提交到仓库（`.env` 已 gitignore）。

**Q39 串口协议为什么有 schema_version 和这么多字段？**
A：为了可追溯和诚实。`schema_version` 保证协议演进兼容，`seq`/`device_ts` 定位数据，`raw_value`/`calibrated_value` 区分原始与标定值，`calibration_version` 追溯标定版本，`sensor_state` 表达传感器健康状态。旧协议 `{"v":..}` 仍兼容。

**Q40 你们借鉴了哪些开源代码？**
A：前端图表用 Apache ECharts（Apache-2.0 许可证，本地化 `static/echarts.min.js`），固件 OLED 驱动用 MicroPython 官方 `ssd1306.py`（MIT 许可证）。我们只做调用，不把开源功能包装成原创；HX711 读取、规则引擎、双模式数据源均为自行实现。
